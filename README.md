# AUREO — a studio of essentials

A Brazilian fashion e-commerce project, built as an independent project from
[Ember & Oak](https://github.com/FelipeFeerreira/ember-oak-coffee).
Brazilian Portuguese storefront, BRL prices, PostgreSQL catalogue, clothing variants and a
brand dashboard.

[Desktop preview](docs/screenshots/aureo/desktop.jpg) · [Mobile preview](docs/screenshots/aureo/mobile.jpg) · [Verification](docs/TESTING.md)

**A working demo environment, not yet cleared for real sales.** Seed photos, measurements,
compositions, popularity and stock are illustrative. There are no invented orders or
revenue. Checkout accepts Stripe **test** credentials only and confirmation depends on a
signed webhook. Pix is not enabled.

## Ubuntu: getting started

Verified requirements: Node **24.21.0**, npm **11.19.0**, Git **2.53.0**, Docker Engine
**29.1.3**, Docker Compose **2.40.3**. Use Node 24 (`.nvmrc`). Docker Desktop is not needed.

```bash
git clone https://github.com/FelipeFeerreira/aureo-fashion.git
cd aureo-fashion
# If nvm is installed:
nvm use
npm ci
cp .env.example .env.local  # FIRST install only; never overwrite your credentials
chmod 600 .env.local
npm run db:up
npx prisma migrate deploy
npm run db:seed
npm run admin:token
npm run dev
```

Store: **http://localhost:3200**. Admin: **http://localhost:3200/admin**.
The private admin key lives in `.env.local`, generated by `admin:token`. Open that file
locally to use it. It is never sent as a URL or included in public JavaScript. Changing it
revokes existing sessions. Do not publish that file.

The `aureo` database uses `127.0.0.1:5440` and the Docker volume `aureo_pgdata`; tests use
`aureo_test` in the same container. That does not touch the database or the original
repository. The public repository is `FelipeFeerreira/aureo-fashion`, main branch `main`.
In this development copy the local branch is `aureo`, the publishing remote is `origin` and
the inherited `foundation` remote has push disabled.

If Docker does not respond, install/enable Docker Engine and the Compose plugin for your
Ubuntu release as per the official docs. Check `docker info` and socket permissions. Do not
run `docker compose down -v` if you want to keep the database.

## Configuration

Copy only the values you need into `.env.local` or your hosting secret manager.
`.env.example` documents the variables, without external credentials.

| Variable | Purpose |
|---|---|
| `DATABASE_URL` | Runtime PostgreSQL |
| `DIRECT_URL` | Optional direct connection for migrations |
| `TEST_DATABASE_URL` | Local database ending in `_test` |
| `ADMIN_TOKEN` | 32–256 character key, server only |
| `NEXT_PUBLIC_SITE_URL` | HTTPS origin in production; localhost allowed in development |
| `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET` | Stripe test/sandbox and webhook signing only |
| `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET` | Persistent media storage |
| `ANTHROPIC_API_KEY` | Optional assistant; leave empty to avoid API usage |
| `NEXT_PUBLIC_ASSISTANT_ENABLED` | `true` shows the discreet assistant |
| `RESEND_API_KEY`, `RESEND_FROM` | Optional confirmations; without a key, local log only |
| `DEMO_MODE` | Keep `false`; the inherited cleanup routine is destructive and demo-only |

Brand identity and drafts are editable in **Brand and content**. The default brand is AUREO.
Categories come from the database. Colours and sizes come from variants. Base colours and
spacing live in `src/app/globals.css`; primary colour, hero and announcement are editable.
The default logo is typographic and follows the configured name.

## Implemented flows

- Editorial homepage, collection, new arrivals, editorial highlights, categories and newsletter.
- Database-paginated catalogue (12 pieces), search, min/max price, colour, size, availability
  and sorting. Filters live in shareable URLs.
- Product page with gallery per colour, zoom, measurements, composition, care, variants, SKU,
  unavailability per combination and related items. No real front/back photos are available:
  replace the references before publishing merchandise.
- Favourites and bag persisted in this browser. Drawer, bag page, quantities, server-validated
  coupon (`DEMO10` in the seed) and address with validated postcode/state.
- Sale prices respect start/end dates; promotion dates in the dashboard are UTC.
- Test checkout in BRL, webhook confirmation, private tracking by order number and e-mail,
  SKU/colour/size/price snapshots and atomic stock per variant.
- Authenticated admin: create/edit/archive products, variants, stock, photos, measurements,
  prices, categories, content, orders, customer history and test-mode indicators.
- Authenticated upload, format/size/pixel validation, metadata stripping, WebP, previews,
  drag-and-drop, accessible ordering buttons, cover and association by colour.
- Optional assistant with catalogue/stock/measurements/order tools, limits, isolated sessions,
  and no free model prose published as commercial fact.
- Explicit, versioned newsletter consent, with unsubscription from the browser that subscribed.
  No campaign is ever sent.
- SEO, sitemap, robots, structured data, responsive images, error/loading states, keyboard
  dialogs and reduced-motion preference.

## Database and migrations

```bash
npx prisma generate
npx prisma migrate deploy      # apply existing migrations
npx prisma migrate dev --name description_of_change  # schema development
npm run db:seed
```

The seed is idempotent, preserves existing products and refuses `NODE_ENV=production`.
It uses `sample=true`. Never run a demo seed against a commercial database.
Migrations are additive: old fields stay for compatibility with the inherited tests and
infrastructure. `ProductVariant` is the authority for fashion stock; `Product.stock` is not
used to sell clothes. Removed variants are deactivated, not deleted when they belong to
orders. Archiving preserves history. SQL constraints prevent negative stock and invalid
promotions/coupons.

## Checkout and delivery

Read [CHECKOUT.md](docs/CHECKOUT.md). Configure a **test** Stripe account, an `sk_test_...`
key, forward the webhook with the Stripe CLI and set `whsec_...`:

```bash
stripe listen --events checkout.session.completed,checkout.session.expired \
  --forward-to localhost:3200/api/stripe/webhook
```

Only the signed event confirms payment; visiting the success page never does. The suite
simulates the provider but uses the real SDK for signatures and real PostgreSQL for
transactions. The real hosted test checkout needs your credentials.

`src/lib/fashion/payments.ts` is the provider interface. Today it only registers the
Stripe test/card adapter. Integrating Pix requires an adapter, its own signed asynchronous
events, provider validation and reconciliation tests. Swapping a key is not enough. No
production adapter is enabled.

Real shipping is not integrated. The postcode is validated; the page states unavailability.
The R$ 0,00 shipping is **a test condition only**, not a commercial offer.
Stock is not reserved during checkout: two confirmations competing for the last unit produce
one `PAID` order and one `PAYMENT_REVIEW`, never negative stock. Before selling, implement
reservations with expiry or an operational review-and-refund flow. The dashboard never
invents payment confirmation.

## Persistent images

Read [ADMIN.md](docs/ADMIN.md). Configure Cloudinary on the server and restart the app.
Without credentials the form explains that upload is disabled. There is no fallback to
ephemeral disk. Upload limited to 5 MB, JPEG/PNG/WebP, 40 megapixels; Sharp decodes, strips
metadata and caps resolution. Delivery uses Next Image and an allow-listed domain.

Deleting an image on the product **unlinks** it; the original stays in Cloudinary for
recovery. Uploaded files that are never saved can be orphaned: establish an administrative
cleanup routine with a retention window. No automatic remote deletion happens in this
project. See [photo credits and limits](docs/PHOTOGRAPHY.md).

## Verification

```bash
npm run typecheck
npm run lint
npm test
npm run test:integration
npx playwright install chromium
npm run test:e2e
npm run build
npm audit --omit=dev
npm audit
```

Integration tests refuse to run outside a local `_test` database.
E2E uses desktop Chromium and Pixel 7. The owner test needs a local `ADMIN_TOKEN`; traces and
screenshots for that test are disabled so no credential is recorded. External upload is
intercepted in the UI test: it proves editing/ordering/persistence, not connectivity to a
Cloudinary account. External payment is mocked too. Older coffee-interface tests are kept in
`tests/foundation-e2e`, outside the AUREO suite. Inherited security and transaction tests
remain active.

## Build, operation and deployment

```bash
npm ci
npx prisma generate
npx prisma migrate deploy
npm run build
npm run start
```

Use Node 24, persistent PostgreSQL, tested backups, TLS and a trusted proxy that overwrites
`x-forwarded-for`. Configure the real public origin, server-side secrets, logs with retention
and body limits at the proxy. Never expose the brand token or personal data in screenshots.
Admin cookies are Secure in production: use HTTPS.

Before launch: real licensed data/photos, reviewed policies, company contact and
identification, shipping, Brazilian payments with validated webhooks and security,
reservation/refund, e-mail verification for sensitive order access, LGPD processes and
marketing opt-out, admin access recovery, observability, backups, real-provider tests and a
load/accessibility review. Customers and reports in the dashboard show the latest 100 orders;
totals use the whole database. There are no customer accounts or cross-device favourite
sync. No deployment, real charge, domain, external account or e-mail was created or sent.
